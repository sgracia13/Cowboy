Evidence · last run October 19, 2026

Does the sorting work? Here’s what we checked.

Four rounds, eleven public repos, about 28,000 merged pull requests, and the claims written down before each round ran. All of it is below, including what failed.

Short answer. Not proven yet. The careful pen has not beaten chance in any round: not the original rules, not revised ones, and not rules fitted to each repo’s own history. The easy pen held up pooled in every round, but in one repo (Kibana) it didn’t. Round 4 measured effort in lines read instead of pull requests flagged, and the careful pen did worse than random there: a 10-line PR was about as likely to be reverted as a 1,000-line one. What works so far is the measuring: Cowboy can show any repo what actually got reverted, and whether a rule would have caught it. A separate test of common habits found none that went with fewer reverts everywhere, so habits are judged per repo too.

Why careful loses here

A pull request’s chance of being reverted barely changes with size, while lines change a thousandfold. Careful leans toward big PRs: 11–19% of PRs but 32–49% of the lines. So per line read, it finds less than picking at random.

What a team can use

If review time tracks lines read, a quick look at every small PR finds more of what later gets reverted than a deep look at a few big ones. That fits the one claim that has held every round: the easy pen is as safe as the smallest PRs, no more and no less.

What this can’t tell

Reverts are one kind of trouble, and big PRs are harder to revert, so they may get fixed forward instead. Counting only reverts may understate trouble in big PRs. Follow-up fixes were too sparse in these repos to check.

03 · Habits

Do good habits mean fewer reverts? Not everywhere.

We asked whether three habits visible in git history go with fewer reverts: no shortcuts (no silenced warnings, skipped tests and the like), tests changed with the code, and linking an issue. The corrected numbers are in the second column. PyTorch supplies 1,629 of the 1,699 reverts, so it decides the pooled result; without it, no habit reaches a verdict.

Why tests “did worse”

PyTorch’s merge bot reverts fast, mostly for breaking tests or internal builds. A pull request that changes tests is likelier to break tests. That says what PyTorch reverts for, not that writing tests is a bad habit.

What we built from it

No cross-team “practices score”: the data doesn’t support one. Cowboy’s Habits page shows each repo its own shares, and only says a habit “holds here” when that repo’s history shows it.

What this can’t tell

Reviews, approvals, checks before merge and disclosed agent help aren’t in git history, so they weren’t tested. A live Cowboy install reads them from the git host.

Revised rules (round 2)

Careful PRs were reverted 1.08× as often as average (range 0.78× to 1.39×). The revisions made the pen smaller in two of three repos, but not better: the original rules did about the same here.

Fitted rules (round 3)

A pen half the size of the defaults’ (12% of PRs vs 24%) with a higher hit rate: 1.37× average vs 1.10×. But the range (0.87× to 1.93×) includes chance, so it can’t be claimed. And months without enough history fell back to the defaults, which supplied 8 of its 17 catches.

Where fitting worked, and where it didn’t

In Kibana it kept picking the CI configuration folder, and that carried over: those PRs were reverted about 3.1× as often in the following months (5 reverts, so still thin). In next.js it picked single files with three to five reverts each, and last quarter’s trouble files weren’t next month’s.

08 · How the tests work

Plan first, data second.

The claims were written down first

The four claims, the alternatives and the pass mark were committed to the repo before the comparison ran. The commit time is the proof. The plan also said: if a claim fails, this page says so.

The data

Merged PRs from November 2025 to September 2026 in five public repos, each sorted by Cowboy’s current rules. “Had trouble” means reverted within 30 days, found by Cowboy’s own after-merge engine from the repo’s history. A repo needs 20 reverted PRs to count.

Two mistakes we caught

The parser. The first run on Sentry, Grafana and n8n used Cowboy’s older import finder, not the parser it ships. Re-run with the shipped parser, “careful beats chance” no longer holds there either. This page shows the re-run. The sample. The plan called the sample random. It wasn’t: every reverted PR was kept, plus a random slice of the rest. That made reverts look four to five times more common than they are. The first run, unweighted, said claim 1 held. Weighted back to each repo’s real mix, it doesn’t. This page reports the weighted run; the unweighted one is in the results file.

09 · Can you trust the measuring?

The parts were checked against outside tools.

Blast radius

100%

of 250,319 JavaScript and TypeScript imports in Sentry, Grafana and n8n found, and wherever the TypeScript compiler could resolve an import, 99.9% or more went to the same file it picks. Every file TypeScript says has 20+ importers, Cowboy caught. Python imports matched Python’s own parser.

Revert detection

255

reverted PRs found by both Cowboy’s engine and an earlier, separate count across the five repos. They disagreed on 17: 11 only the earlier count found, 6 only the engine found. Neither is a hand-checked truth.

Repeatable

same in, same out

The sorting is fixed rules with sorted iteration: the same PR and the same code give the same pen and the same reasons, every run.

10 · What this doesn’t show

Read these before quoting a number.

Tuned in-sample

The rules were adjusted while looking at Sentry, Grafana and n8n. The held-out test is the fairer one, and it’s the weaker result.

Reverts only

Broken main, follow-up fixes and incidents need data public repos don’t keep. Reverts are the clearest kind of trouble, and also the rarest.

No team in the loop

Nobody reviewed differently because of a pen. This checks whether the pens point at risky PRs, not whether a team using Cowboy ships fewer of them.

Small numbers

Supabase has 25 reverted PRs and PostHog 18. That’s enough to see a big effect, not a small one.

11 · What happens next

Stop guessing what’s risky. Show each team what was.

Lead with the measuring

Three rounds say no fixed rule set, and no simple fit, reliably finds risky PRs across repos. What did work every time is the part that measures: finding what got reverted, tying it back to the PR, and checking any rule against it. That’s what Cowboy will lead with.

More kinds of trouble

Reverts are rare: a few a month even in busy repos, too few to judge a rule quickly. Counting main breaking after a merge and confirmed follow-up fixes gives several times more events to learn from.

Real teams, if they choose

Cowboy can export a counts-only summary (no names, paths or code). Teams that share theirs add evidence from live use, which no replay can.

Open test: does a local AI model beat the rules? The test is built and its claims are written down, but no real model has run it yet. Help us run it: every registered run goes here, whichever way it comes out.

12 · Run it yourself

Every number here comes from scripts in the repo.

The evidence folder has the claims, the results and the comparison script. Collect a repo’s PRs, sort them, replay the after-merge engine, then compare:

git clone --filter=blob:none --bare https://github.com/OWNER/REPO repo.git
python3 scripts/eval/collect_sort.py repo.git OWNER/REPO full.jsonl checkout 2> collect.log
python3 scripts/eval/checkout_src.py repo.git COMMIT checkout   # COMMIT: last line of collect.log
go run ./cmd/cowboy-sortlab -in full.jsonl -checkout OWNER/REPO=checkout -out sorted.jsonl
go run ./cmd/cowboy-replay -sorted sorted.jsonl -patches full.jsonl -collectlog collect.log -git OWNER/REPO=repo.git -out replay
python3 scripts/eval/evidence/compare.py sorted.jsonl replay collect.log
