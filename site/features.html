Sort what’s coming. Check what happened.

Cowboy sorts every new pull request as it arrives, so you know where to look first. It looks back at the ones that merged, to see what went wrong and whether the sorting, or any rule of yours, would have caught it. And it shows which of your team's habits pay off in your repo, then turns all of that into instructions your coding agents follow. The screens here come from the demo that ships with Cowboy, which runs on a made-up repo, except where a caption says otherwise. All of it is free. This is a preview release: the last section says what's tested and what isn't yet.

Sorting, as pull requests arrive.

Every new pull request lands in easy, normal or careful by fixed rules, with the reasons written on it, and agent work is tagged. Treat the pens as a starting point: the next part shows how Cowboy checks them on your repo.

Rules you can read.

Sensible defaults out of the box. Change them per repo with one small file on your default branch. A pull request can't loosen its own rules.

  • Pick your own sensitive paths.
  • Name the bot accounts your agents use.
  • Turn the experimental check for unmarked pull requests off.

Looking back, after they merge.

This is the part that earns trust. Cowboy follows every merged pull request, traces trouble back to the one that caused it, and checks whether the pens, or simpler rules, would have pointed at it. In our own tests the careful pen didn't beat simpler rules, and Cowboy will tell you the same if it's true on your repo.

Trace trouble to the pull request.

Cowboy follows every merged pull request for 30 days and ties what happened back to it: reverted, broke main, needed a fix, or caused an incident.

  • Reverts and a broken main count by themselves. Follow-up fixes and incidents from Sentry, PagerDuty or any tool are suggestions a person confirms.
  • Don't wait a month: rate the last 90 days of merged pull requests now. Nothing is written to your git host.
  • A track record for every agent, by area of the code, and a report card for every rule.
  • A tamper-evident record of every sort, move, approval and outcome, ready to export.

Example numbers.

Test your rules against simple alternatives.

A rule that flags a quarter of your pull requests will catch some trouble by luck. So Cowboy gives the same share of pull requests to simple alternatives and compares.

  • Your careful pen against “largest first”, “most files touched first” and a random pick. Your easy pen against the same share of smallest pull requests.
  • Counts and a likely range for every result, in words: outperformed, no demonstrated advantage, did worse.
  • Fewer than 20 pull requests with trouble in a repo? It says “Not enough evidence yet” and stops there.
  • The same calculation as the published evidence, on the After merge page or with cowboy evaluate.

Guide your agents.

Coding agents follow the instructions file in your repo. Cowboy writes a section for it from what it already knows, so agents open pull requests your team can review quickly.

  • Which paths and files get a careful review, and the size that gets the quickest one.
  • The shortcuts Cowboy flags, only for the checks you have switched on.
  • This team's habits, with evidence quoted only where your history backs it.
  • How to say an agent helped, so reviewers know what they're reading.
  • Copy or download it from the Habits page, or run cowboy guide --write AGENTS.md. It replaces only its own section, between markers. Cowboy never commits it for you.
  • Agents can check themselves before a PR exists: cowboy check sorts local changes and lists any shortcuts, and cowboy mcp gives Claude Code, Cursor and other agents the same check, the repo’s rules and a file’s trouble history as tools. Local and read-only.
  • Orchestrators can listen in: signed events as pull requests are sorted, moved, merged and found to cause trouble, and a read-only API with per-agent scorecards. Cowboy reports; your orchestrator decides what to do about it.
AGENTS.md
<!-- cowboy:guide start -->
## Working in vercel/next.js

### What gets a closer review
- Changes under `auth/**`, `migrations/**`, `payments/**` are sent for careful review. Keep them small.
- Pull requests of 50 lines or fewer, in 2 folders or fewer, get the quickest review. One concern per PR.

### Don't take these shortcuts
- Don't silence warnings or type errors to get checks passing. Fix the cause, or say why the warning is wrong.
- Don't skip or delete tests to get a change through.

### This team's habits (last 90 days)
- **Tests with code**: 59% of pull requests here do this.
- **No shortcuts**: 82% of pull requests here do this.

### Say when an agent helped
- Add a Co-authored-by trailer naming the agent.
<!-- cowboy:guide end -->

What's in the preview.

Cowboy is a preview release. Here's what has been tested on real code, what works but is still in preview, and what isn't built yet.

Tested on real code

  • The sorting rules, tested on about 28,000 merged pull requests from eleven public repos: the easy pen mostly held up; the careful pen didn't beat simpler rules. See the evidence.
  • The comparison against simple alternatives: it reproduces the published evidence exactly.
  • Labels, the one comment, doubles, moving a pull request and noticing closes, live on a real GitHub repo.
  • The catch-up sweep and the dashboard login.
  • Blast radius (how many files use a changed file), checked against the TypeScript compiler and Python's own parser on Sentry, Grafana and n8n. It downloads the repo from your git host itself, so no local copy is needed.

Works, in preview

  • Setup in the browser: run cowboy, connect with your GitHub CLI login or a token, pick repos, and switch labelling on when ready. Tested against a stand-in for GitHub, not yet github.com.
  • The GitHub App route for a team server: tested against a stand-in for GitHub, not yet github.com.
  • GitLab, on gitlab.com or your own server: tested against a stand-in for GitLab's API, not yet gitlab.com.
  • Forgejo and Gitea.
  • Storage in SQLite, saved change by change. An older install's data file is moved over by itself on first start.
  • The Habits page and the agent guide: covered by tests and run on the demo's next.js history. Reviews and checks need a live install to fill in.
  • Local model notes and the "off task?" flag.
  • Review requests to code owners, and strays: covered by tests, not yet seen on a live repo.
  • The experimental check for pull requests with no agent mark.
  • The weekly tally in Slack or email: covered by tests, not yet sent to a real workspace.
  • After-merge tracking: revert detection checked on two years of Sentry, Grafana and n8n history (it traced 70–99% of reverts to their PR); the rest tested against stand-ins for GitHub, Sentry and PagerDuty.

Not built yet

  • Review requests to teams like @org/team. Today it's individual people.
  • A signed Mac app.
  • Rules suggested from your own history, for a person to approve. The fitting is built and tested, but it didn't beat chance on fresh repos, so it isn't switched on.
